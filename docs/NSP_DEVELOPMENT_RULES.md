# 야간근무지침 — DEVELOPMENT RULES

> Codex / Claude 등 AI 코딩 에이전트가 반드시 따라야 하는 개발 규칙이다.  
> 기능 구현보다 **구조 유지, 단일 책임, 데이터 일관성, 수정 가능성**을 우선한다.

## 1. 가장 중요한 규칙

1. **하드코딩으로 콘텐츠를 박아 넣지 않는다.**
2. **같은 데이터를 여러 곳에서 관리하지 않는다.**
3. **기능마다 Manager를 새로 만들지 않는다.**
4. **기존 코드와 역할이 겹치는 클래스 / 시스템을 추가하지 않는다.**
5. **문제가 생겼다고 전체 구조를 갈아엎거나 대규모 리팩터링하지 않는다.**
6. **문서에 없는 기능을 임의로 추가하지 않는다.**
7. 모호한 설계는 구현 전에 사용자에게 질문한다.

## 2. 단일 진실 공급원 (Single Source of Truth)

다음 정보는 반드시 한 곳에서만 실제 값을 소유한다.

- 현재 날짜 / 게임 단계
- 봉쇄 코어 진행도
- 자재 / 전력
- 직원 능력치 / 스트레스 / 위치 / 업무 / 격리 여부
- 시설 방 상태
- 현재 활성 금기
- 사건 로그

UI는 값을 복사해서 별도 상태로 보관하지 말고 **표시만** 한다.

## 3. 권장 구조

정확한 클래스명은 기존 프로젝트와 협의해 결정하되 역할은 겹치지 않게 한다.

### Session / Game State
- 날짜
- 현재 Phase
- 코어 진행도
- 자재 / 전력
- 승패

### Facility Simulation
- 직원 이동
- 업무 진행
- 방 상태
- 실시간 사건

### Taboo Rule System
- 활성 금기
- 위반 조건 검사
- 정해진 결과 실행 요청

### AI Service
- Claude API 통신 전담
- 프롬프트 구성 또는 Context Builder와 연결
- timeout / retry / fallback
- API 결과를 게임 상태에 직접 적용하지 않음

**같은 역할의 `SomethingManager`, `SomethingController`, `SomethingSystem`을 중복 생성하지 않는다.**

## 4. 데이터 주도 설계

다음 콘텐츠는 코드의 if/else 체인에 직접 박지 않는다.

- 직원 프로필
- 능력치
- 성격 3문장
- 금기 정의
- 금기 위반 조건 / 결과 ID
- 업무 정의
- 방 정보
- 날짜별 콘텐츠

Godot Resource, JSON, 또는 프로젝트에서 합의한 데이터 형식으로 분리한다.

예:

```text
employee_id
codename
stats
personality_lines
role
```

```text
taboo_id
condition_type
condition_params
consequence_type
consequence_params
```

단, 데이터 형식은 구현 전에 사용자와 확인한다.

## 5. 매직 넘버 금지

다음 값을 여러 스크립트에 직접 반복 작성하지 않는다.

- 최대 일수 5
- 직원 최대 수
- 스트레스 최대치
- 살인 최대 횟수
- API timeout
- 이동 속도

공용 Config 또는 데이터 파일에서 관리한다.

## 6. 씬과 로직 분리

- UI 씬은 게임 규칙을 직접 판정하지 않는다.
- CCTV 씬이 살인 여부를 결정하지 않는다.
- 직원 Sprite가 자신의 전역 데이터를 소유하지 않는다.
- UI 버튼은 시스템에 명령을 전달하고 결과를 반영한다.

## 7. 직원 AI와 게임 판정 분리

Claude는 **NPC의 자아처럼 보이는 표현 계층**이다.

### Claude가 결정 가능
- 어떤 말투로 답할지
- 알고 있는 사실 중 무엇을 언급할지
- 허용된 행동 후보 중 어떤 행동을 시도할지

### Godot가 결정
- 해당 행동이 가능한가
- 실제 이동 가능한가
- 금기를 위반했는가
- 살인이 성공하는가
- 설비가 고장나는가
- 자원이 얼마나 변하는가
- 승패

Claude가 반환한 결과를 그대로 실행하지 않는다.

## 8. Claude API 규칙

### API Key
- API Key를 `.cs`, `.gd`, `.tscn`, `.tres`, JSON 등 프로젝트 파일에 직접 작성하지 않는다.
- GitHub에 절대 커밋하지 않는다.
- 로컬 환경변수 또는 Git 추적 제외 설정을 사용한다.
- 최종 공개 빌드에서 키가 노출되지 않는 구조를 사용한다.

### 호출 빈도
- 매 프레임 호출 금지.
- 모든 NPC가 주기적으로 API를 호출하게 만들지 않는다.
- 실제 대화 또는 중요한 행동 판단이 필요한 순간에만 호출한다.

### Context
NPC에게 필요한 정보만 준다.

- 자기 프로필
- 성격 3문장
- 자기 능력치 / 스트레스
- 현재 업무 / 위치
- 직접 알고 있는 사실
- 최근 대화 요약

일반 직원에게 진범, 전체 로그, 다른 직원의 비밀 등 알 수 없는 정보를 주지 않는다.

### Structured Output
행동 판단은 자유 문장이 아니라 제한된 구조를 사용한다.

예시 개념:

```json
{
  "action": "WAIT | WORK | TALK | MOVE | LIE | SABOTAGE | KILL_ATTEMPT",
  "target_id": "...",
  "reason": "..."
}
```

실제 스키마는 구현 단계에서 별도로 확정한다.

### 실패 대응
- timeout 처리
- 제한된 retry
- API 오류 시 로컬 fallback
- JSON 파싱 실패 시 안전한 기본 행동

**인터넷/API가 끊겨도 프로토타입과 심사용 빌드가 완전히 멈추면 안 된다.**

## 9. 살인마 로직 규칙

- 살인마는 매일 무조건 살인을 시도하지 않는다.
- 목적은 코어 복구 방해 + 정체 은폐다.
- 살인은 허용 조건이 만족될 때만 후보 행동에 포함한다.
- 전체 5일 성공 살인은 최대 2회.
- 하루 최대 1회.
- 플레이어가 잘 관리하면 0회 가능.
- Godot가 살인 가능 조건과 성공 여부를 검증한다.

## 10. 금기 규칙

- 금기는 데이터로 정의한다.
- 동일한 금기 결과를 여러 씬에서 따로 구현하지 않는다.
- 위반 결과는 예측 가능해야 한다.
- “랜덤 체력 -20” 같은 의미 없는 패널티보다 실제 운영 사건을 발생시킨다.

## 11. 이벤트 / 로그

모든 중요한 사건은 공용 로그 시스템을 통해 기록한다.

예:
- 직원 방 입장/퇴장
- 업무 시작/종료
- 재배치
- 금기 위반
- 정전
- CCTV 단절
- 거짓 지시가 실제 행동으로 이어진 경우
- 사망 / 격리

추리와 AI 대화가 이 로그를 그대로 읽는 것은 아니다. 각 NPC가 알 수 있는 정보만 별도 필터링한다.

## 12. 코드 품질

- 한 스크립트가 지나치게 많은 역할을 가지지 않게 한다.
- 반대로 10줄짜리 기능마다 Manager를 만들지 않는다.
- 함수와 클래스 이름은 역할을 명확히 표현한다.
- 복붙 코드가 두 군데 이상 반복되면 공통화 여부를 검토한다.
- 순환 의존성을 피한다.
- 노드 경로 문자열을 여러 곳에 하드코딩하지 않는다.
- `GetNode("../../...")` 같은 취약한 경로 남발 금지.
- 기능별 public API를 명확히 한다.

## 13. 작업 방식

에이전트는 매 작업 전:

1. 관련 문서를 읽는다.
2. 현재 프로젝트 구조를 확인한다.
3. 이미 존재하는 비슷한 코드가 있는지 검색한다.
4. 수정할 파일과 구현 계획을 짧게 설명한다.
5. 필요한 경우 사용자에게 질문한다.
6. 작은 단위로 구현한다.
7. 실행/빌드 오류를 확인한다.
8. 수정 파일과 변경 내용을 요약한다.

## 14. 하지 말 것

- 요청하지 않은 대규모 리팩터링
- 기존 씬 통째 삭제 후 재생성
- 동작하는 시스템을 새 Manager로 중복 구현
- 임시 코드라는 이유로 캐릭터명/금기/날짜를 코드에 박기
- Claude에게 전체 게임 상태를 통째로 전달
- API 응답이 게임 상태를 직접 변경하게 하기
- 오류가 난다고 예외를 무시하거나 빈 catch로 덮기
- 사용자 승인 없이 신규 시스템 추가

## 15. 스코프 보호

이 프로젝트에서 기본적으로 추가하지 않는 것:

- 피로 / 호감도 / 신뢰도 / 정신력 등 추가 수치 상태
- 자유 타일 기지 건설
- 여러 엔딩 트리
- 10명 이상의 직원
- 매일 별도 미니게임
- 필요 없는 인벤토리

새 기능 제안이 필요하면 먼저 **기존 핵심 루프에 정말 필요한지** 사용자에게 확인한다.
