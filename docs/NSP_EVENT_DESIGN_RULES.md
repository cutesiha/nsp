# NSP — EVENT DESIGN RULES

> 금기, 시설 사고, 이상현상, 파괴공작 콘텐츠를 추가할 때 반드시 따라야 하는 설계 규칙.
>
> 사건의 개수를 늘리는 것이 목적이 아니다.
> 플레이어가 사건을 예측하고, 예방하고, 대응하고,
> 이후 원인을 추론할 수 있게 만드는 것이 목적이다.

---

# 1. 모든 사건은 6가지 정보를 가져야 한다

새 사건을 만들 때 반드시 아래 항목을 정의한다.

## 1) 발생 조건 (TRIGGER)

질문:
"정확히 어떤 게임 상태일 때 이 사건이 발생 가능한가?"

조건은 Godot가 판정할 수 있는 객관적인 값이어야 한다.

좋은 예:
- 해당 방 CCTV가 OFF
- 직원이 방에 혼자 있음
- 발전기 점검을 30초 이상 방치
- 특정 방에 직원 2명 이상 존재
- 현재 다른 방에 긴급 사고가 활성화됨

나쁜 예:
- 플레이어가 한눈팔고 있을 때
- 분위기가 위험할 때
- 범인이 기회를 봤을 때

모호한 자연어 상태를 사용하지 않는다.

---

## 2) 사전 징후 (WARNING)

질문:
"터지기 전에 플레이어가 위험을 눈치챌 수 있는가?"

가능하면 모든 주요 사고에는 사전 징후가 있어야 한다.

사용 가능한 징후 예:
- 경고 아이콘
- 조명 깜빡임
- 이상음
- 전화 보고
- 직원의 비정상적인 체류
- 업무 진행 속도 이상
- CCTV 화면 이상
- 시설 로그

사고가 아무 예고 없이 즉시 발생하지 않도록 한다.

플레이어가 징후를 놓쳐 사고가 발생했다면
"게임이 억까했다"가 아니라
"내가 놓쳤다"고 느낄 수 있어야 한다.

---

## 3) 결과 (CONSEQUENCE)

질문:
"사건이 발생하면 무엇이 실제로 달라지는가?"

결과는 기존 시스템에 영향을 준다.

사용 가능한 결과 예:
- 전력 감소
- 자재 생산 정지
- 직원 스트레스 상승
- 통로 봉쇄
- 업무 중단
- CCTV 사용 불가
- 코어 복구율 감소
- 직원 이동 제한

한 사건에 너무 많은 결과를 동시에 부여하지 않는다.

권장:
주 결과 1개
보조 결과 최대 1개

예:

발전기 고장
→ 전력 문제

환기 고장
→ 스트레스 문제

정비실 고장
→ 자재 문제

각 사고의 역할을 명확하게 분리한다.

---

## 4) 대응 방법 (RESPONSE)

질문:
"이미 사건이 터진 뒤 플레이어가 무엇을 할 수 있는가?"

반드시 플레이어가 개입할 방법이 있어야 한다.

예:
- 기술 직원 재배치
- 업무 우선도 변경
- 전력 재분배
- 직원 호출
- 구역 봉쇄
- 위험 직원 격리

대응 방법이 없는 사건을 남발하지 않는다.

---

## 5) 예방 방법 (PREVENTION)

질문:
"플레이어가 잘했다면 애초에 막을 수 있었는가?"

대응과 예방은 구분한다.

예:

발전기 과열

예방:
- 미리 발전기 점검 업무 수행

대응:
- 이미 고장난 뒤 기술 직원을 보내 수리

파괴공작

예방:
- CCTV 감시
- 직원 2인 배치
- 의심 직원 격리

대응:
- 사고 발생 후 수리
- 로그 확인
- 용의자 추적

게임 숙련도가 올라갈수록
'사고를 잘 수습하는 플레이'에서
'사고 자체가 일어나지 않게 하는 플레이'로 발전해야 한다.

---

## 6) 남는 흔적 (EVIDENCE)

질문:
"사건 이후 플레이어가 원인을 추론할 정보가 남는가?"

특히 파괴공작은 반드시 흔적을 남긴다.

사용 가능한 흔적:
- 작업실 출입 로그
- 특정 시간대 위치 기록
- CCTV 기록
- 설비 상태 변화 시간
- 업무 진행도 이상
- 직원 목격 정보
- 전화 진술
- 직원 진술과 시스템 기록의 모순

좋은 예:

22:14 — 여우 환기실 입장
22:16 — 환기 설비 정지

여우 진술:
"그 시간에는 저장고에 있었습니다."

→ 기록과 진술의 모순을 플레이어가 직접 발견.

나쁜 예:

[시스템]
범인은 여우입니다.

정답을 직접 알려주지 않는다.

---

# 2. 사건은 단독으로 끝나지 않아야 한다

좋은 사건:

발전기 과열
→ 최대 전력 감소
→ CCTV를 끔
→ 감시 사각 발생
→ 파괴공작 기회 발생
→ 직원 위치 로그에 모순 발생
→ 추리

나쁜 사건:

발전기 고장
→ 수리 버튼 클릭
→ 정상 복구
→ 끝

사건은 가능하면 다른 시스템의 선택을 어렵게 만들어야 한다.

---

# 3. 파괴공작 설계 규칙

파괴공작자는 무작위로 플레이어를 공격하지 않는다.

파괴공작 후보 행동은
플레이어가 만든 취약 상태를 기반으로 활성화한다.

대표적인 취약 상태:
- CCTV 사각
- 조명 OFF
- 단독 직원
- 봉쇄로 고립된 공간
- 금기 위반으로 발생한 혼란
- 다른 긴급 사고 처리 중
- 중요 시설의 인력 공백

조건을 만족했다고 반드시 행동하지 않는다.

파괴공작자는:
- 정체 은폐
- 코어 복구 방해
를 우선한다.

살인은 가장 좋은 행동이 아닐 수 있다.

---

# 4. 일반 사고와 파괴공작을 구분한다

같은 형태의 고장이라도 원인이 다를 수 있다.

예:

환기 정지 A
- 점검 업무 방치
- 일반 시설 사고

환기 정지 B
- 파괴공작자가 설비 파손
- 의도적 사건

플레이어는 결과만 보고 즉시 원인을 알 수 없어야 한다.

대신 로그, CCTV, 진술 등을 통해
일반 사고인지 파괴공작인지 추론할 수 있어야 한다.

---

# 5. 사건 우선순위

한 직원 또는 방에서 여러 사건 조건이 동시에 만족될 수 있다.

모든 사건을 동시에 실행하지 않는다.

권장 우선순위:

1. 현재 진행 중인 치명적 금기 이상현상
2. 이미 발생한 긴급 시설 사고
3. 파괴공작 / 살인 후보
4. 일반 시설 사고
5. 일반 직원 행동

실제 우선순위 구현은 기존 시스템 구조를 확인하여 조정할 수 있다.

같은 유형의 사건이 연속해서 과도하게 발생하지 않도록
쿨타임 또는 일일 제한을 사용한다.

---

# 6. 금지 사항

다음 방식으로 난이도를 만들지 않는다.

- 이유 없는 랜덤 사고
- 랜덤 즉사
- 플레이어가 알 수 없는 숨겨진 수치만으로 판정
- 대응 방법이 없는 사고의 반복
- 한 사건에 4~5개의 패널티 동시 적용
- 새로운 게이지를 계속 추가
- 파괴공작자가 플레이어 정보를 전지적으로 알고 행동
- CCTV를 보고 있는데도 아무 설명 없이 범행 성공
- 로그에 범인을 직접 표시
- Claude API가 게임 상태를 직접 결정

난이도는 정보 부족이 아니라
서로 충돌하는 선택에서 만든다.

---

# 7. 사건 추가 체크리스트

새 사건을 추가하기 전에 아래 질문에 YES라고 답할 수 있어야 한다.

- [ ] 발생 조건을 Godot가 명확하게 판정할 수 있는가?
- [ ] 플레이어가 사전에 위험을 알아챌 방법이 있는가?
- [ ] 사건 발생 후 대응할 방법이 있는가?
- [ ] 잘하면 예방할 수 있는가?
- [ ] 다른 시스템의 선택에 영향을 주는가?
- [ ] 파괴공작이라면 추리에 사용할 흔적이 남는가?
- [ ] 결과가 랜덤 억까처럼 느껴지지 않는가?
- [ ] 새로운 불필요한 게이지를 추가하지 않았는가?

하나라도 핵심 항목이 NO라면 구현 전에 다시 설계한다.
