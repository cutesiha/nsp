# NSP 저사양 대응 — PHASE 2 ~ 5 결과

PHASE 1(측정)은 [PERFORMANCE_BASELINE.md](PERFORMANCE_BASELINE.md) 에 있다. 이 문서는
**그 측정을 근거로 무엇을 고쳤고, 고친 뒤 얼마나 달라졌는지**만 적는다.

- 측정 기계: Intel Core i3-10110U (4스레드) + Intel UHD Graphics · 1800×980 · 디버그 빌드
- 렌더러: Forward+ / D3D12 (바꾸지 않았다 — 아래 §5 참조)
- **GPU 프레임 시간은 Godot 4.7 이 내주지 않는다 — 측정 불가.** 아래 ms 는 모두 CPU 쪽
  프레임 간격(실제 체감 프레임)이고, GPU 병목의 크기는 "끄면 얼마나 도는가" 로만 추정했다.

## 0. 먼저 — 측정 방법을 바꿨다

PHASE 1 의 §B 표(`docs/perf/raw_probe.md`)는 ①②③… 을 **한 번씩 차례로** 재서 늘어놓은
것이다. 그 표를 그대로 믿고 PHASE 3 을 시작했다가, 다시 재 보니 **숫자가 뒤집혔다.**

| 토글 | 차례로 잰 값(PHASE 1) | 짝지어 잰 값 |
|---|---|---|
| CCTV 3D 월드 렌더 OFF | −2.6 ms | **−0.4 / +1.7 ms** (이득 없음) |
| CRT SubViewport 전부 OFF | −7.8 ms | **+1.1 / +4.8 ms** (이득 없음) |

이 노트북은 측정 내내 성능이 흔들린다(§PERFORMANCE_BASELINE G). 떨어져 있는 두 줄의
차이는 토글 때문인지 기계 때문인지 구분되지 않는다. 그래서 `PerfProbeRun` 을 고쳐
**토글마다 바로 앞에 기준을 한 번 더 재고 그 짝과만 비교**하게 했다
(`docs/perf/probe_paired.md`, `docs/perf/probe_phase34.md`).

> **PHASE 3 의 전제였던 −7.8 ms 와 −2.6 ms 는 측정 흔들림이었다.** 실제로는 없는
> 이득이었고, 따라서 그 두 가지는 **고치지 않았다.** 이미 있는 게이팅
> (`UpdateActiveViewports` · `UpdateCctvWorldViewport`)이 제 몫을 하고 있다.

## 1. PHASE 2 — 점프스케어가 멈추는 문제

### 무엇이 문제였나 (측정)

점프스케어 1회차와 2회차의 차이가 전부 "처음이라서" 였다.

| | 호출 → 화면 표시 | 그 중 모델 로드 |
|---|---|---|
| 1회차 | 142.29 ms | **88.77 ms** |
| 2회차 | 31 ms | 0 ms |

0.1초짜리 연출에서 111 ms 는 성능 문제가 아니라 **연출이 죽는 것**이다 — 놀라야 할
순간에 화면이 멈춘다.

### 무엇을 고쳤나

1. `MonsterActor` 가 한 번 읽은 모델을 **버리지 않는다.** 전에는 괴물이 바뀔 때마다
   `QueueFree` 하고 다음에 다시 읽었다. 모델 노드는 메시·텍스처를 **공유**하므로
   (PackedScene 인스턴스는 리소스를 복제하지 않는다) 숨겨 두는 비용은 노드 몇 개뿐이다.
2. `MonsterWarmup` — 근무가 시작되기 전(시작 화면)에 괴물 3종을 미리 인스턴스화하고,
   32×32 오프스크린 뷰포트에 **한 번 실제로 그려** 셰이더 변형과 텍스처 업로드까지
   미리 치른다. 괴물 하나마다 프레임을 넘겨 처리해 준비 자체가 끊김이 되지 않게 한다.
3. `AdminDeathDirector` 가 **사망하는 순간** `new MonsterActor()` 하던 것을 없앴다.

### 중간에 내가 만든 버그 둘 (둘 다 측정/점검으로 잡았다)

- **미리 읽어 둔 모델이 숨어서도 계속 움직였다.** `Visible=false` 는 그리는 것만 막고
  `AnimationPlayer` 는 그대로 돈다. 준비를 넣자마자 평상시 FPS 가 30 → 18 로 떨어졌다.
  → 쓰지 않는 모델을 `ProcessMode.Disabled` 로 재운다(`MonsterActor.Sleep`). 22.5 로 회복.
- **`_root` 까지 재웠다가 되돌렸다.** `HorrorDirector` 는 배우를 거치지 않고
  `_faceActor.Root.Visible = true` 를 직접 켠다 — 그 경로로는 깨어나지 못해
  **애니메이션이 멈춘 채 뜰 뻔했다.** 최적화하려던 바로 그것을 깨뜨릴 뻔한 것이다.
  재우는 것은 sway(쓰지 않는 모델) 쪽만으로 충분하다.

### 고친 뒤 (측정)

| | 전 | 후 |
|---|---|---|
| 첫 점프스케어의 모델 로드 | 88.77 ms | **0.00 ~ 0.42 ms** |
| 첫 점프스케어 호출 → 표시 | 142.29 ms | **49.06 ms** |
| 둘째 점프스케어 호출 → 표시 | 31 ms | 31.19 ms (그대로) |

### 연출이 그대로인지 — 숫자가 아니라 눈으로

`scenes/debug/EntityProbe.tscn` 을 새로 만들어 **준비 켬 / 끔(nowarm)** 두 번 돌려 비교했다.

```
   사전 준비 **켬**
   PASS  쓰지 않는 모델은 재워 두었다      (준비된 모델 1개 — 자는 중 1 · 깨어 있음 0)
   PASS  연출 전에는 꺼져 있다
   PASS  화면에 떴다
   PASS  쓰는 모델은 깨어 있다
   PASS  클립이 돌고 있다                  (클립 위치 0.000s → 0.118s — 실제로 진행한다)
   PASS  의도한 자세(Seek 지점)에서 떴다
   PASS  연출이 끝나고 사라졌다
```

`scenes/debug/ScareShot.tscn` 으로 CCTV 점프스케어 3종(결번자·아기·거미)도 다시 찍어
**셋 다 제 모델로, 서로 다른 각도로** 뜨는 것을 확인했다.

## 2. PHASE 3 — SubViewport · CCTV 3D 월드

### 하지 않은 것과 그 이유

위 §0 대로, CCTV 3D 월드를 끄거나 CRT 화면들을 끄는 것은 **짝지어 재면 이득이 없다.**
이미 있는 게이팅이 제 몫을 하고 있다는 뜻이다. 그래서 건드리지 않았다.

### 한 것 — 안 쓰는 화면의 **렌더 타깃을 놓아 준다**

`SubViewport` 는 `Disabled` 로 내려 두어도 자기 크기만큼 텍스처를 계속 쥐고 있다.
화면 프로그램이 스무 개인데 한 번에 CRT 에 붙는 건 둘뿐이라, 나머지 열여섯 장이
내내 자리를 차지했다. 시스템 메모리를 나눠 쓰는 내장 GPU 에서는 이게 그냥 메모리가
아니라 **다른 것이 밀려나느냐 마느냐**다.

지킨 두 가지:

- **`AddScaledView` 로 등록된 것만** 줄인다 — 안의 UI 가 고정 크기 프레임에 들어 있어
  뷰포트 크기를 바꿔도 배치·입력 좌표가 흔들리지 않는 것들이다.
- **떨어진 뒤 4초 있다가** 줄이고, 다시 붙일 때는 `Configure` 보다 **먼저** 제 크기를
  돌려준다. 2×2 짜리 텍스처가 한 프레임이라도 CRT 에 뜨면 화면이 한 덩어리 색으로 번진다.
- CCTV 화면(`_cctvVp`)은 제외했다 — 화면에서 내려가 있어도 증거 사진의 원본이 된다.

| | 전 | 후 |
|---|---|---|
| 같은 장면 · 같은 품질(Low)에서 GPU 메모리 | 659.2 MB | **631.9 MB** (−27 MB) |

프레임 시간 차이는 ±2 ms 안쪽으로 **이 기계의 측정 흔들림과 구분되지 않는다.**
이 변경의 근거는 메모리지 프레임이 아니다.

> 실제로 화면이 번지지 않는지는 `RestNoteShot`(근무 → 휴게 → 인터뷰로 화면이 통째로
> 바뀌는 경로)으로 다시 찍어 확인했다. 여섯 장 모두 제 해상도로 선명하게 나온다.

## 3. PHASE 4 — 품질 옵션

### 3-1. 버그: 실행 중에 품질을 바꿔도 CRT 는 그대로였다

`ControlRoom3DController.RenderScale` 은 처음 읽은 값을 `static` 에 캐시하는데
**무효화하는 곳이 없었다.** 그래서 설정 창에서 품질을 내려도 메인 3D 만 바뀌고,
CRT 모니터와 CCTV 3D 월드는 **만들어질 때 정해진 해상도 그대로** 계속 그려졌다.
플레이어 입장에서는 "낮음으로 내려도 별로 안 빨라진다" 가 된다.

→ `OnQualityChanged()` 가 캐시를 비우고, `AddScaledView` 가 적어 둔 등록부
(`_surfaces`)를 돌며 **뷰포트 크기와 안쪽 프레임 배율을 같이** 다시 잡는다.
(하나만 바꾸면 내용이 화면보다 작아져 검은 여백이 생기거나 넘쳐서 잘린다.)

#### 3-1-1. 그 수정이 만든 고장 — 클릭이 엉뚱한 곳에 들어갔다

위 3-1 을 넣자마자 **근무 배치 화면에서 마우스가 어긋났다.** 양을 눌렀는데 늑대가
잡히는 식이다. 화면은 멀쩡해 보여서 더 나쁘다.

원인은 한 줄이었다. 3D 화면의 클릭 판정은 전부

```
화면에 쏜 광선 → UV(0~1) → 뷰포트 픽셀 좌표 = UV × 뷰포트 크기
```

인데, `MonitorScreen3D` 만 그 **뷰포트 크기를 `Configure` 때 한 번 복사해 두고 있었다.**
뷰포트 크기가 평생 안 바뀐다는 전제였고, 3-1 이 바로 그 전제를 깼다. 프레임 배율은
같이 바뀌니 **그림은 맞고 좌표만 배율만큼 어긋난다.**

→ 복사하지 않고 그때그때 읽는다(`CanvasSize => TargetViewport.Size`).
책상 위 배치표와 관리자 패드는 원래부터 `_vp.Size` 를 그때그때 읽고 있어서 멀쩡했다.

같은 수정에서 하나 더 잡았다 — **안 쓰는 화면 놓아 주기(§2)가 넘쳤다.**
`_surfaces`(AddScaledView 등록부)에는 **주인이 따로 있는 화면**(배치표 · 관리자 패드 ·
경보 단말)도 들어 있는데 그것까지 2×2 로 줄이고 있었고, CRT 가 어두운 단계에서는
**붙어 있는 화면**도 `Once` 로 한 장만 그린 뒤 엔진이 `Disabled` 로 내려놓아
"안 쓰는 화면" 과 구분되지 않았다. 이제 **이 컨트롤러가 직접 켜고 끄는 CRT 화면만**,
그리고 **어느 모니터에도 붙어 있지 않을 때만** 놓아 준다.

`scenes/debug/SurfaceInputProbe.tscn` 으로 고정했다 — 배치 화면의 직원 카드를
**창 좌표로 실제 클릭**해 그 직원이 잡히는지 보고, 품질을 실행 중에 바꾼 직후에도
다시 본다. 되돌려 보면 그대로 재현된다:

```
# 고치기 전 (CanvasSize 를 복사해 두던 때)
################ 품질 Low → VeryLow 로 바꾼 직후 ################
   FAIL  창 좌표 (698, 413) 를 눌렀더니 **sheep** 가 잡혔다 (잡힌 것: wolf)
   FAIL  창 좌표 (694, 256) 를 눌렀더니 **cat** 가 잡혔다 (잡힌 것: wolf)

# 고친 뒤
################ 결과: 22 PASS / 0 FAIL ################
```

### 3-2. 점 광원 그림자 — 여기가 draw call 의 절반이었다

| 그림자를 켠 광원 13개 | |
|---|---|
| SpotLight3D | 2 (모니터 1·2 화면빛) |
| **OmniLight3D** | **11** (제어실 천장등 + CCTV 월드 각 방의 RoomLight) |

스포트라이트의 그림자는 그림자 맵 **한 장**이지만, 점 광원의 그림자는 큐브맵 —
**여섯 면**이다. 장면을 여섯 번 더 그린다. 끄고 재 보면:

| | draw call | 렌더 오브젝트 |
|---|---|---|
| 켬 | 785 | 2538 |
| 끔 | **444** | **1993** |

**높음 · 보통은 건드리지 않았다.** 조명과 공포 분위기를 그대로 두라는 요구가 있고,
실제로 천장 광원의 그림자가 빠지면 책상 위 기기들이 바닥에서 뜬 것처럼 보인다.

### 3-3. 새 칸 — "매우 낮음"

| 품질 | 3D 배율 | 빛 번짐 | 그림자 아틀라스 | 점 광원 그림자 |
|---|---|---|---|---|
| 높음 | 1.00 | ○ | 4096 | ○ |
| 보통 | 0.82 | ○ | 2048 | ○ |
| 낮음 | 0.72 | ✕ | 1024 | ○ |
| **매우 낮음** | **0.58** | ✕ | **512** | **✕** |

**"낮음" 을 더 내리지 않고 칸을 새로 만든 이유** — 0.72 라는 값은 그냥 고른 것이 아니라,
0.65 에서 전화 받는 손가락이 뭉개져 모션이 달라 보여서 올려 둔 값이다. 그 판단을 뒤집어
모두의 "낮음" 을 흐리게 만드는 대신, 더 필요한 사람만 한 칸 더 내려갈 수 있게 했다.

설정 창은 `QualityLevels.Length` 로 순환하므로 자동으로 네 칸이 된다. 저장 파일에는
숫자로 들어가므로 **새 항목은 반드시 뒤에** 붙였다(가운데 끼우면 전에 "낮음" 으로
저장한 사람이 다른 품질로 켜진다).

`docs/perf/probe_phase34.md` ⑪ — 근무 중 · CCTV 켜짐 상태에서 품질만 바꿨다.

| | 평균 ms | 평균 FPS | draw call | GPU 메모리 |
|---|---|---|---|---|
| 낮음 | 35.3 | 28.3 | 785 | 628.6 MB |

메인 3D 배율만 바뀌고 draw call 은 그대로였을 것이다.

## 4. 건드리지 않은 것

요구대로, 그리고 측정 결과가 근거를 주지 않아서.

- **게임 규칙 · 직원 AI · 사건 발생 조건 · 심문 · 추리 · 증거 · 엔딩 판정** — 손대지 않았다.
- **귀신·괴물의 등장 타이밍 · 연출 시간 · 사운드 동기화** — 손대지 않았다.
  `MonsterThreatTest` 59 PASS / 0 FAIL, `GhostModeTest` 40 PASS / 0 FAIL 로 확인.
- **공포 연출을 지우거나 느리게 하는 방식** — 쓰지 않았다. PHASE 2 는 오히려 연출이
  **제때 뜨도록** 고친 것이다.
- **캐릭터 모델** — 그대로다. 저퀄리티로 되돌리지 않았다.
- **괴물 모델의 중복 복제** — 하지 않았다. 배우마다 노드는 따로지만 메시·텍스처·
  애니메이션 **리소스는 공유**된다(PackedScene 인스턴스는 리소스를 복제하지 않는다).
  실제로 준비를 넣은 뒤 GPU 메모리가 늘지 않았다.
- **헤어 스튜디오 원본 라이브러리** — 시작 시 로딩하지 않는다. 건드리지 않았다.

## 5. 렌더러는 바꾸지 않았다

`project.godot` 은 Forward+ / D3D12 그대로다. 프로젝트 전체를 Mobile 이나 Compatibility 로
바꾸는 것은 하지 않았다 — 요구에 어긋나고, 무엇보다 **이 기계에서 비교해 보지 않았다.**
렌더러는 엔진 초기화 전에만 고를 수 있어 실행 중 A/B 가 불가능하고, 따로 빌드해 재 보지
않은 채 "Mobile 이 더 빠르다" 고 적는 것은 재지 않은 수치를 적는 일이다.

필요하면 다음에 이렇게 재면 된다: `project.godot` 의 렌더러만 바꾼 사본을 따로 두고,
같은 세션 안에서 두 실행을 번갈아 돌려 `PerfBaselineRun` 보고서를 짝지어 비교한다.

## 6. 남은 것 · 재지 못한 것

- **GPU 프레임 시간 · GPU 병목의 정확한 위치** — Godot 4.7 이 내주지 않는다. 측정 불가.
  "끄면 얼마나 도는가" 로만 추정했다.
- **점 광원 그림자 정책이 닿지 않는 곳** — 런타임에 새로 생기는 점 광원(연출용 임시
  광원 등)은 다음 `ApplyPointShadowPolicy()` 호출 전까지 그림자를 켠 채다. 지금은
  품질을 바꿀 때와 제어실이 준비된 직후에 한 번씩 돈다. 실측 장면에서는 전부 잡혔다.
- **전체 회귀 테스트는 돌리지 않았다.** 이번 변경과 직접 닿는 것만 돌렸다 —
  `MonsterThreatTest`(59/0) · `GhostModeTest`(40/0) · `ScheduleConsoleTest`(33/0) ·
  `SurfaceInputProbe`(22/0), 그리고 캡처 확인으로 `ScareShot` · `EntityProbe` · `RestNoteShot`.
- **"매우 낮음" 에서 전화 받는 손 모션이 어떻게 보이는지** — 0.58 은 0.65 보다 낮다.
  수치상 더 뭉개진다. 이 칸을 쓸지 말지는 보고 정할 문제라 기본값은 바꾸지 않았다
  (기본은 여전히 "높음", 저장된 설정이 있으면 그것).
